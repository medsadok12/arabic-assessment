# الأداء في منصة عارم — رقم قبل ورقم بعد

**القاعدة الأولى (القسم 12.4):** أي تحسين أداء يُثبت بقياس قبل وبعد: حجم حزمة، أو حجم استجابة، أو زمن. «كود سليم نظرياً» بلا رقم لا يُقبل، ولا يُبلَّغ الأستاذ محمد بتحسّن لم يُقَس.

## 1. شخّص أولاً — من أين يأتي البطء؟

1. **حجم الاستجابة:** استدعِ المسار وقِس حجمه بالبايت. إن وجدت `data:image` أو `data:audio` داخل JSON فهذا هو السبب، فقد كان 314 صورة و71% من استجابة قائمة كاملة.
2. **حجم الحزمة:** شغّل `next build` واقرأ عمود `First Load JS` للصفحة قبل التعديل وبعده.
3. **الاستعلامات:** هل هناك `await` متتالية لاستعلامات مستقلة؟
4. **الكاش:** اقرأ ترويستَي `x-vercel-cache` و`cache-control` من الدومين الحقيقي، فالبطء قد يكون محتوى قديماً لا بطئاً.
5. **أصل خارجي:** سكربت أو مجسّم 3D أو خط من CDN خارجي قد يكون محجوباً في شبكة المدرسة، فيُعلّق الصفحة.

## 2. قواعد ثابتة

| المجال | القاعدة |
|---|---|
| الصور | تُرفع إلى Supabase Storage وتُخزَّن روابطها فقط. تُصغَّر في المتصفح قبل الرفع بـ`resizeImageToWebp(file, maxSize, quality)` من `lib/image-resize.js`. ممنوع base64 في الجداول. |
| الأصوات | تُرفع إلى Storage بـ`lib/game-audio.js`. الصفوف القديمة تُصلَح ذاتياً عند القراءة (`healAudioRows`). |
| المكوّنات الثقيلة | تُستورد بـ`next/dynamic`: three.js، والرسوم البيانية، ولوحات الولي والمعلم. هكذا نزلت `/dashboard` من 1133.8KB إلى 695.3KB. لوحة المعلم داخل لعبة تُحمَّل بـ`dynamic(..., { ssr: false })` حتى لا يحمّلها الطالب أبداً. |
| تنبيه | `dynamic()` لا يمرّر `ref`؛ استعمل استيراداً ثابتاً إن احتجت `ref`. |
| الاستعلامات | الاستعلامات المستقلة داخل `Promise.all` واحد. أي استعلام جديد يُضاف داخله، لا كـ`await` بعده. |
| الأعمدة | `select('col1, col2')` محدّد، لا `select('*')` على جداول فيها أعمدة كبيرة. |
| الكاش | لا `s-maxage` على محتوى يعدّله المعلم (`aarem-feature` §5). الكاش مسموح فقط لمحتوى لا يتغير من اللوحة. |
| الأصول | GLB والسكربتات والخطوط مستضافة ذاتياً في `lms/public/`. |
| الحركة | `transform` و`opacity` فقط في الحركات المتكررة، و`requestAnimationFrame` لا `setInterval`. أوقف حلقة three.js حين لا تكون ظاهرة، واحترم `prefers-reduced-motion`. |
| القوائم الطويلة | لا تُعِد رسم القائمة كلها عند كل ضغطة مفتاح. ما يُحسب من القائمة يكون في `useMemo`، والمفاتيح `key` ثابتة من `id`. |
| Service Worker | ارفع رقم الكاش (`aarem-vN`) مع أي تغيير جوهري في سلوك التطبيق. |
| أخطاء hydration | أي تحذير `Text content did not match` أو `Switched to client rendering` يعني أن الجزء يُرسم مرتين. من أسبابه المؤكَّدة: نص `<style>{\`…\`}</style>` فيه `'` أو `"` أو `>`؛ والعلاج `dangerouslySetInnerHTML` (يحرسه `lib/style-blocks.test.js`). ومن أسبابه أيضاً قيمة تختلف بين الخادم والمتصفح، مثل `Date.now()` و`Math.random()` و`window` أثناء الرسم. التقط التحذير من `page.on('console')` في Playwright. |

## 3. القياس عملياً

```bash
# حجم الحزم — قبل وبعد (متغيرات وهمية، لا أسرار)
cd lms && NEXT_PUBLIC_SUPABASE_URL=https://localtest.supabase.co \
  NEXT_PUBLIC_SUPABASE_ANON_KEY=local-test-anon SUPABASE_SERVICE_ROLE_KEY=local-test-placeholder \
  ./node_modules/.bin/next build | grep -E "^(├|└|┌)" > /tmp/before.txt
```

- **حجم بيانات حقيقية:** استعلام SQL للقراءة فقط عبر Supabase MCP، مثل `select sum(length(image_url)) …` و`count(*) filter (where image_url like 'data:%')`.
- **زمن متصفح:** Playwright مع `page.metrics()` أو `performance.getEntriesByType('navigation')`، على أبعاد الآيباد والجوال.
- أبلغ النتيجة كجدول «قبل ← بعد» بالأرقام.

## 4. لا تفعل

- لا تطبّق «تسريعاً» يعالج عرضاً ويترك السبب. أربعة commits سابقة (Edge runtime، تقسيم حزمة، كاش، تحديد أعمدة) فشلت لأن السبب كان base64.
- لا تضع كاش CDN على مسار يعدّله المعلم لتسريعه، فيظهر للمعلم أن تعديله لم يُحفظ.
- لا تحذف طبقة أمان في استوديو الأبطال (مهلة 12 ثانية، المسار السريع `mv.loaded`) بحجة السرعة.
